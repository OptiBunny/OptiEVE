# OptiEVE

A private, read-only overview and connector for EVE Online character and corporation data. It uses EVE SSO authorization code flow with PKCE and exposes the following tools through `/mcp`:

| Tool | Data returned |
| --- | --- |
| `connection_status` | Connected characters, granted scopes and setup URLs |
| `character_overview` | The personal dashboard’s six summaries, with per-section permissions, coverage and freshness |
| `character_training_report` | Compact skill, attribute and planned-training briefing with upcoming finishes and omitted-row counts |
| `character_clone_report` | Separate active-implant and stored-clone evidence, full received counts and bounded previews without clone names or locations |
| `character_calendar_report` | One calendar-summary batch with response and date-window counts, a bounded UTC schedule and explicit continuation evidence |
| `wallet_activity_report` | One journal page’s cash-flow totals and categories, with the latest thirty returned UTC dates and explicit omissions |
| `open_orders_report` | Separate remaining bid/asking values, full-response expiry evidence and bounded type/order previews |
| `read_private_data` | One page of orders, assets, wallet transactions or wallet journal |
| `contracts_report` | One contracts-page briefing with status/type counts and up to twenty upcoming offer expirations |
| `market_transactions_report` | Compact gross purchase/sale activity for one owned transaction batch, with bounded date/type groups and explicit cursor coverage |
| `inventory_reference_report` | One asset-page reference subtotal using public average prices, with pricing coverage, up to twenty types/categories and explicit omissions |
| `industry_jobs_report` | Reported job states, active-job schedule and compact upcoming/attention lists for one owned jobs response |
| `planetary_colony_report` | One explicitly selected colony’s reported extractor schedule, independent source freshness and up to twenty extractor-detail rows |
| `read_character_data` | An allowlisted character dataset, with dataset-specific parameters and pagination |
| `read_corporation_data` | Wallet balances, assets and name/location lookups, order history, contracts and items/bids, industry jobs, blueprints, facilities, structures, mining extractions, freelance jobs, projects and your selected character’s contribution |
| `resolve_names` | Public EVE names for supplied IDs |
| `public_market` | One page of public regional orders for an item |
| `manufacturing_item_search` | Bounded public item search with recipe IDs and official catalog provenance |
| `manufacturing_recipe` | Official manufacturing inputs, output units, required skills and base time |
| `manufacturing_catalog_status` | Latest official SDE manifest compared with the pinned catalog |
| `manufacturing_requirements` | Deterministic material quantities from runs, ME and an explicit facility multiplier |
| `manufacturing_market_history` | Public regional history with cache evidence; not station liquidity |
| `manufacturing_industry_costs` | Manufacturing system index and requested input adjusted prices |
| `manufacturing_station_quote` | Exact NPC-station depth, minimum fills, owned-order exclusions and expiry |
| `assess_manufacturing` | Owner-scoped stock, blueprint, skills, funding, market depth and conditional economics |
| `manufacturing_compare` | Up to five alternatives under one context and completion-time freshness check |
| `manufacturing_plan` | Combined production and shopping plan with shared stock, wallet, copy runs and depth |
| `wallet_history_status` | Private character-wallet history settings and saved coverage |
| `wallet_history_report` | Saved cash-flow totals, daily series and categories |
| `configure_wallet_history` | Explicit opt-in, pause and retention settings in the private app |
| `capture_wallet_history` | Explicit manual capture into already enabled private history |
| `clear_wallet_history` | Explicit erasure of saved financial history and disablement |

The application cannot place orders, change prices, move assets or spend ISK. Corporation reads require the appropriate scopes and character roles.

## Workspace navigation

The sixteen workspaces are grouped under Character, Finance, Operations and Setup. Larger layouts show grouped buttons; compact layouts offer the same destinations in a native selector. Changing workspaces keeps each view's existing loading controls. Leaving a data workspace clears its displayed results through the existing unmount behavior. Navigation choices are not stored, and switching views does not enable history or start a background collector.

## Saved wallet history and reports

The Wallet activity tab includes **Saved wallet history** for one connected character. It is off by default. Load its status, explicitly enable it with a retention choice of 30, 90 or 365 days, then choose **Capture** when you want to save the currently available journal window. There is no background collector. Pausing stops new captures; erasing clears saved financial data and disables collection. Disconnecting the character also removes its application history. Corporation wallets continue to use the existing on-demand views; corporation history is not collected.

Saved reports support the last **7, 30, 90 or 365 days**, independently of the 30/90/365-day retention setting. Select **Compare with the preceding period on the next load** before loading to show two adjacent windows from the same saved observations, with a shared-scale incoming/outgoing chart, exact UTC boundaries and signed observed differences. In the private chat, ask to compare saved wallet activity with the preceding period; the existing `wallet_history_report` tool accepts `comparePrevious: true`. Comparison is off by default and does not enable history, capture data or change retention.

Comparison windows end at report time and exclude future-dated entries until their timestamp is reached; ordinary reports retain their existing one-minute timestamp tolerance. The previous window excludes the boundary shared with the current window, so an entry is counted once. Retention-clipped windows, missing amounts and empty observations remain explicit; differences are unavailable when either period lacks known totals, has missing amounts or extends outside current retention. Even a numeric difference compares observed activity only, not complete-period growth, profit or wallet balance. Missing days never become zero activity.

The dashboard and five wallet-history chat tools use the same service. In the private-use chat, ask to check history settings, enable a chosen retention period, capture the journal, or report incoming/outgoing ISK by day and category. Enable, capture and erase are application-storage changes and have write annotations; they never write to EVE. A report request does not implicitly enable or collect history. Tool results themselves may remain in the calling chat.

A capture accepts at most four journal pages and 10,000 events, within one request deadline. Repeated events are deduplicated and conflicting records fail safely. Saved history is bounded to 10,000 events and one MiB of plaintext before encryption; a full store rejects new captures instead of silently discarding unexpired records. Only IDs needed for deduplication, UTC event times, reported amounts and fixed categories are retained, with bounded capture evidence. Descriptions, counterparties, reasons, balance fields and raw responses are excluded. History is encrypted in the private D1 database with the existing token key and a separate user/character binding.

Reports show observed **cash flow, not profit, net worth or a reconstructed balance**. They preserve missing amounts, source freshness and partial page coverage. Missing days are omitted, never filled with zeros; all advertised pages do not establish complete calendar coverage. Exact-decimal totals cannot recover precision already lost in provider JSON numbers. EVE supplies a limited journal window, so this feature cannot reconstruct activity that was never captured. Retention filters expired events from reads; physical cleanup occurs during later history mutations, not on a timer. Reducing retention can delete saved events. Erasure and disconnect do not remove older chat results or external backups.

The additive migration in `drizzle/` must be applied before this Worker version runs. It leaves existing configuration and encrypted authorizations intact, adds a connection lifecycle marker and an initially empty history table. Existing installations remain opted out. Preserve the encryption key during upgrades. See [storage and retention guidance](SECURITY.md#storage-and-retention).

## Manufacturing planning in chat

The Manufacturing workspace supports public product search, owned blueprint pages, individual assessments, candidate comparison and a combined production/shopping plan. Select the connected character, personal or corporation resources, market, facility and explicit cost assumptions before loading. Blank costs mean unknown; enter zero only when that assumption is intended. Inputs and results remain in memory and clear when the context changes or the workspace is left. The same operations are available through the MCP tools using existing read permissions.

Comparison accepts one shared context and up to five jobs. Rankings compare modeled instant-sale economic profit for qualifying alternatives at their selected batch sizes; they are not profit-per-hour rankings or a jointly funded portfolio. The combined plan allocates stock and verified blueprint-copy runs in submitted job order, totals upfront cash against one wallet, and quotes aggregated material deficits and output quantities against shared market depth. It does not count planned output as available input stock, future sales as funding, or an original blueprint as multiple concurrent job slots. Missing costs, incomplete depth and uncertain evidence remain visible.

Open `/demo` to explore the same workspace with clearly labeled synthetic fixtures, including missing evidence and limited-resource scenarios. It makes no EVE, account-status or manufacturing API requests and stores no inputs or results. Demo values are examples, never live prices or account evidence. The deployment's existing audience policy still applies to this route.

`assess_manufacturing` takes one blueprint and at most twelve material types. Corporation resources require an explicit wallet division and, when using owned stock, explicit hangar divisions. Personal funds are never substituted. Available funds use the received numeric wallet balance's decimal representation, floored to whole ISK cents with integer arithmetic; sub-cent fractions cannot increase affordability. Malformed, negative, nonfinite or out-of-range balances remain unknown. Select the market NPC station and manufacturing system separately; an optional accessible structure can verify its system, but does not establish manufacturing-service access, rigs or fees. Stock may be selected at verified facilities, observed offices or containers with validated parent chains and inherited hangar divisions. The default private page budget is three; callers may request up to fifty pages and 50,000 asset rows. The workspace exposes these bounds under Data read limits, alongside a public market-page limit of one to four (default two). Larger limits remain subject to the shared deadline and do not promise complete coverage. Unknown pages, missing ancestors, cycles, unsupported selected storage and stale data cannot establish zero stock or affordability.

Supply the owned blueprint item and page, or explicitly choose a prospective blueprint. Verified owned ME and copy runs override caller claims. Prospective acquisition, blueprint availability for a new job, facility access and hauling remain conditions. Fees and overhead use decimal strings: omitted or null values mean unknown, while an explicit zero is a scenario assumption. Installation may use a supplied quote or the current system index and adjusted input prices with explicit cost/tax multipliers. Recipe quantities use conservative whole-job upward rounding; estimated item value uses undiscounted recipe inputs. Owned inputs retain their forgone net sale value; replacement cost and additional cash are shown separately. Instant-sale and hypothetical listed-sale results are separate, and no estimate establishes realized profit or a guaranteed sale.

Every assessment has a shared 55-second deadline, checks account ownership and corporation consistency, and rechecks evidence expiry at completion. Depth uses exact-station public orders, effective minimum quantities and explicit own-order exclusions. Ranged bids at other locations are omitted. Regional history is context, not station demand. Incomplete exclusions, insufficient depth, missing costs, or an outdated/unverified recipe catalog keep results conditional. Private results remain in request memory and in the calling chat's normal result history, with no application archive or background refresh.

The public catalog is a derived snapshot of [CCP's official SDE](https://developers.eveonline.com/static-data/tranquility/latest.jsonl), with build, release and content hashes in `app/data/manufacturing-catalog.json` and attribution in the adjacent NOTICE. The runtime only checks the small latest-build manifest; it never downloads or replaces recipes automatically. Catalog changes are reviewed and rebuilt with the application source. Update to a reviewed source version when a newer catalog is needed, and retain its provenance and attribution.

## Operations overviews

**Open orders** shows one personal response or one corporation page, with order-side counts and exact remaining buy-bid and sell-asking values. Each value multiplies the received unit-price representation by reported remaining units and sums each side separately without cent rounding. Personal results exclude corporation-placed orders; an omitted optional buy flag means Sell. These quoted values are not cash, escrow, proceeds, market valuation, profit or guaranteed fills, and prior provider/JSON precision cannot be recovered. Quantities stay separate by item type and side. Item labels use the pinned public catalog; issuer identities, locations and private names are omitted.

The value charts independently rank the top twelve buy and sell item types, while 100-row tables keep every returned type and order reachable. Type/side and reported-expiry date/window controls filter only the detail table. Five fixed-clock windows cover past or current expiry, the next 24 hours, after 24 hours through seven days, after seven through thirty days, and later. A sparse calendar shows at most 31 UTC dates in the next thirty rolling days. Expiry is issued time plus duration, not proof of cancellation or completion. Full-response totals keep their scope; local controls make no new reads and reset on refresh or page changes, including repeated provider timestamps.

In the private chat, `open_orders_report` uses the same selected orders response and returns full counts, separate exact quoted values and expiry evidence, with at most twenty ranked types per side and twenty upcoming orders. Total and omitted counts are explicit; unavailable data remains unknown. The preview omits persistent order IDs, issuer/location fields and escrow. Supply an owned `characterId` and `entity`; character orders forbid `page`, while corporation page defaults to 1 and is limited to 500. No additional pages, market prices, history, grants or game writes are requested.

**Blueprint analytics** adds original/copy/original-stack composition, material/time-efficiency distributions and top blueprint types for one selected personal page or all available corporation blueprint pages. Charts count records, while the searchable table distinguishes stack units and each copy's remaining runs. Original and copy quantity sentinels are interpreted explicitly; contradictory rows are rejected. No total across unrelated copy runs, production output, available job slots, valuations or location inference is calculated. Row numbers are response-local, and item/location identifiers and flags are omitted. The existing raw blueprint libraries remain available separately.

These two dashboards reuse the saved market and blueprint read grants, without changing authorization. Corporation market reads remain subject to EVE's Accountant/Trader access and blueprint reads to Director access. Loads are manual, new loads replace prior results, and changing owner or leaving the view clears data. Orders reject responses above 5,000 rows. Personal blueprints and each corporation blueprint page accept at most 1,000 records. Both use strict browser validation, cancellation and visible cache evidence; no history or settings are saved.

The normal corporation blueprint load first collects the blueprint pages ESI advertises, then compares them with corporation assets using the existing asset read permission. Progress distinguishes the two stages and cancellation discards the load. Reads run sequentially under one shared 55-second deadline, with at most 50 pages and 50,000 received records per source and 50,000 combined unique blueprint records. These budgets may stop before the provider's last page. The blueprint-only collection endpoint remains available. Identical duplicates count once with an inconsistency warning; malformed or conflicting pages, changing corporation or pagination, changed within-source cache snapshots, denied/rate-limited reads and failures stop that collection. Each accepted subset remains explicitly limited. Exact tables use bounded local pagination.

**Blueprint asset reconciliation** can reveal additional items omitted from the blueprint endpoint. Raw item identifiers join the two sources only in server request memory and never enter the browser projection. Blueprint-only records are retained; absence from the assets response does not establish lost ownership or an active industry job. Matching identities with conflicting type, copy flag or physical quantity remain flagged, with the blueprint endpoint's evidence preserved rather than overwritten. Each source has independent coverage, consistency and completion-time freshness; their cache timestamps need not match, and the comparison is not an atomic inventory snapshot.

If either source accepts no pages, source overlap remains unknown. Known blueprint or asset records are still displayed, but the charts and table do not label them as exclusive or additional to an unread source. Research-metadata charts cover accepted records only and omit the unread source instead of assigning it zero. Two accepted empty feeds still show zero returned records; partially read paired feeds compare their accepted subsets with explicit coverage limits.

Only types classified in blueprint category 9 by the pinned public SDE qualify as assets-only blueprints. Classification does not depend on names or manufacturing recipes. Unmapped asset types remain unclassified. Additional-item charts distinguish copy and non-copy records using ESI’s optional-boolean contract: an omitted copy flag means false. The bounded table shows the reported quantity and explicitly unknown material efficiency, time efficiency and remaining runs. A false or omitted asset copy flag does not establish an original blueprint, and absent research values never mean zero or unlimited runs. Research-efficiency charts continue to cover blueprint-endpoint records only. Source-overlap and combined-type charts count records, not mixed-item quantities, usable stock, production capacity or value. No extra name or location lookups, saved inventory history or new scopes are introduced.

**All available API pages is not a complete owned library.** ESI has historically imposed a 25,000-blueprint database ceiling, and some container-stored blueprints may be omitted even below it. The current schema does not guarantee a numeric ceiling, so the app follows advertised pages within its own budgets and warns when the historical threshold is reached. No asset scan, missing research data or additional ownership is inferred. See the [official provider-limit issue](https://github.com/esi/esi-issues/issues/1083#issuecomment-503512769), [container-omission issue](https://github.com/esi/esi-issues/issues/611#issuecomment-408416331) and [ESI cache-snapshot guidance](https://developers.eveonline.com/docs/services/esi/best-practices/).

**Inventory** adds personal and corporation asset-page analytics. Category donuts, group bars and reported-location bars count asset records; a record can represent a stack or one item. The searchable type table shows quantities summed only within that type, plus singleton and blueprint-copy metadata. Omitted optional copy flags mean false under ESI’s contract; this does not establish an original blueprint or its research. Filters and table pagination are local to the loaded page. Type/group/category labels come from the checked public catalog; unmapped types retain their IDs and unknown classification. Location IDs and kinds remain as reported: the app does not resolve container ancestry, infer a station, fetch custom item names, or estimate net worth, volume or available manufacturing stock. One provider page replaces the previous page, with a 1,000-row application limit and explicit paging/freshness.

**Inventory reference** is an optional checkbox on the inventory load. It adds one public average-price read only when the selected asset page contains eligible types; toggling the checkbox alone performs no read. The original asset request is reused. Exact per-type quantity × received average price produces a known reference subtotal, separate from the unpriced portion. This is not net worth, a station quote, an appraisal of individual items or guaranteed resale proceeds. Singleton-bearing nonblueprint types can contribute, without assessing assembly, fittings, mutations or condition.

Blueprint types, reported blueprint copies and uncertain classifications are excluded. Missing average prices stay unknown; adjusted industry prices are never substituted. A reported zero price is distinct from a missing price. Pricing failure preserves accepted inventory evidence. Coverage charts distinguish priced, missing, excluded and unavailable types/records; the largest twelve priced types appear on a value chart, and all returned types remain in filterable 100-row table pages. Different item quantities are not added together.

The public price request contains no authentication, character, corporation, location or item-instance selections. Prices are joined to inventory locally in request memory. Each source retains its own cache evidence, rechecked when aggregation completes; the two feeds are not an atomic snapshot. One page replaces the previous page, and no values or history are saved.

In the private chat, `inventory_reference_report` uses the same selected asset page and existing read grant. It preserves full-page pricing coverage and the known subtotal, then shows at most twenty priced types and twenty categories, ranked by exact known reference value with explicit total/omitted counts. It omits locations, item-instance identifiers and raw asset records. Counts and quantities cover only the returned page; excluded and unpriced values are not zero.

**Industry jobs** adds personal and corporation job dashboards: reported-status composition, activity counts, an active-job end-date chart, a filterable timeline and exact UTC job dates. The timeline shows the first 20 matching jobs, with all matching jobs available in 100-row table slices. Summary charts cover the full returned response; local filters affect only the timeline and table. The optional completed-jobs read requests EVE's available history window, up to 90 days. Personal jobs use one unpaged response; corporation jobs use an explicit page. A reported ready job is different from a delivered job, and a past end time does not establish completion. Runs stay per job, with no mixed-activity output total, cost or profit calculation. Installer, completing-character, facility/location and blueprint-item identifiers are omitted. The application rejects responses above 5,000 rows rather than truncating summaries.

The industry schedule separates reported-active jobs into past-end, next 24 hours, days 2–7, days 8–30 and later windows at the load timestamp. A sparse UTC calendar shows future reported ends within thirty rolling days, including partial boundary dates. Ready and paused jobs remain separate provider states. Clicking a window or date filters the timeline and table locally; full-response status and schedule charts retain their original scope.

In chat, `industry_jobs_report` returns the same status counts and schedule, at most ten activity groups, ten upcoming active jobs and ten attention rows, each with total and omitted counts. Attention order is reported-ready, active-past-end, then reported-paused; it does not rank profitability or establish completion. The completed-jobs option is off by default. Only corporation jobs accept a page selector. Missing evidence remains unknown; the report performs no extra reads, automatic paging or collection.

Both views reuse existing asset/industry read grants. Corporation access remains controlled by EVE roles (Director for assets and Factory Manager for jobs). There are no new scopes, credentials, history tables, automatic reads or game-state writes. Their shapes and limits follow the [dated ESI schema](https://esi.evetech.net/meta/openapi.json?compatibility_date=2026-10-31); activity labels come from the pinned official SDE, with unknown numeric activities retained explicitly.

**Trade activity** groups one character transaction batch or one current-corporation wallet division by UTC date, item type and buy/sell side. Character results include only rows explicitly reported as personal; excluded corporation entries remain counted in coverage. Gross purchases and sales use exact arithmetic on the decimal representations of received prices and quantities. They do not include fees or taxes and are not profit, cost basis, wallet balance or net worth. Item names come from the pinned public catalog; unknown types retain their IDs.

Paired purchase/sale charts show the latest thirty returned dates and the twelve most active types, with exact values and explicit omissions. Type ranking uses gross purchases plus gross sales, not profit. All returned date/type/side cells remain available through filters and 100-row local table pages. Filters show their own totals while charts and summary retain the full batch. Quantities remain per item type and side; unlike items are never combined into a single quantity.

Loads are manual and cancellable. Loading an older cursor replaces the current batch; no batches are joined or saved. An inclusive cursor-boundary record can repeat, and a null next cursor does not establish complete history. Missing dates are not filled with zero activity. Changing owner, feed, division or batch, refreshing or leaving the view clears results and filters. The service rejects malformed, duplicate, oversized or inconsistent evidence rather than silently truncating totals.

In the private chat, `market_transactions_report` uses the same existing wallet read grant and one selected transaction batch. It returns full-batch totals, at most thirty included UTC dates and twenty types ranked by gross activity, with total and omitted group counts. Individual transaction IDs, counterparties, locations, journal references and raw cells are omitted. Unknown reports retain null totals and omission counts; no history capture, extra scope or game write is added.

**Contracts** shows one selected character or current-corporation contracts page. It includes reported status and type counts, issued and offer-expiry dates, and optional acceptance/duration fields. Summary counts use the report completion time: outstanding offers at or before that instant are past their reported expiry; the next-24-hours count includes future expiries through the exact boundary. These dates do not change EVE’s reported status.

The offer-expiry chart covers outstanding records only and shows the earliest thirty returned UTC dates with real calendar spacing and explicit omitted-date counts. Every returned date remains selectable. Local status/type/date/contract-ID filters use 100-row table pages, while charts keep full-response counts. Chart selections replace the relevant filters so the selected count matches the table. Changing owner, feed, provider page or loading again clears prior results; provider pages are never combined automatically.

The private-chat `contracts_report` uses the same page and grants. It returns full-page counts and at most twenty outstanding offers whose expiry is after the report timestamp, with total and omitted counts. Unavailable counts remain unknown; a verified empty page remains zero. Titles, counterparties, locations, prices, rewards, collateral, items and bids are omitted. No permission expansion, persistent history, public-name lookup or extra detail read is added.

EVE’s contracts endpoints cover contracts involving the selected issuer, acceptor or assignee, with a documented thirty-day window except for in-progress contracts. An offer expiry is not an accepted courier delivery deadline. Acceptance time and days-to-complete are reported inputs, not a derived deadline or proof of fulfillment, failure, reward or profit. The app rejects a response above 1,000 contracts instead of silently truncating its summaries. [CCP’s dated contracts schema](https://esi.evetech.net/meta/openapi.json?compatibility_date=2026-10-31) and [courier guidance](https://support.eveonline.com/hc/en-us/articles/203218982-Courier-Contracts) describe these distinctions.

**Skills & training** adds a character-manager dashboard for reported total and unallocated SP, skill-group and level charts, a searchable skill list, attributes and remap metadata, and a reported queue timeline with exact UTC dates. Trained and active levels remain separate, including expert-system boosts. The chart does not infer active training, current SP, completion or a precise training rate. Skills may lag until the next EVE login, and queue dates can be absent or already past. Skills, queue and attributes load independently under their existing read scopes, with a shared deadline and per-section freshness. Responses above the application limits of 2,000 skill rows or 1,000 queue rows are rejected rather than silently truncated.

The skill explorer makes every returned skill reachable in 100-row pages. Search by skill name, group name or type ID, and combine exact group, trained level, active level and active-versus-trained filters. Equal group names do not merge distinct group IDs; unmapped groups remain separate. The SP chart shows the largest twenty returned groups, while the group selector includes them all. Selecting a group or level chart label replaces the table filters with that selection. Charts retain full-response totals, and filters reset when the report or character changes. These controls make no additional reads and save no selections.

The training queue also shows disjoint schedule buckets: finish dates already elapsed, the next 24 hours, over 24 hours through seven days, over seven through thirty days, later dates, and missing finish dates. All buckets use the same report-completion timestamp; a date exactly at the boundary belongs to the earlier bucket. The next-thirty-days chart places reported finish dates on a UTC calendar axis and leaves days without dated entries unfilled. Missing dates can hide additional planned work, and a passed finish is not confirmed completion. Local bucket/date/skill filters show the first 20 matching timeline entries and 100-row table pages; the charts continue to cover the full returned queue. Filters clear on a new result or character selection.

In the private chat, `character_training_report` requests those same three feeds for one owned character. It returns SP and level summaries, the ten largest reported skill groups, schedule counts and daily planned finishes, the first twenty upcoming queue entries, and attributes/remap metadata. Omitted group and future-entry counts remain explicit. Section permissions and freshness stay separate; no active-training state, current in-training SP, SP/hour, remap readiness or confirmed completion is inferred. This report adds no history, settings, permission requests or game writes.

**Wallet activity** shows daily incoming/outgoing ISK, net cash flow and fixed activity categories for one explicitly selected journal page. Choose either the character wallet or one corporation wallet division. Amounts are summed with exact integer arithmetic on the received JSON numbers' decimal representations; prior provider or JSON parsing precision cannot be recovered. Missing amounts remain unknown, and days without returned rows are omitted. Transfers are included as movements, so these charts do not establish profit, wealth or historical balances. Loading another page replaces the chart; no pages or accounts are combined. The application accepts at most 2,500 rows in one response. Raw journal entries, counterparties, descriptions, balances and tax fields are excluded from this dashboard's response.

A diverging daily net chart places outgoing-dominant dates left of zero and incoming-dominant dates right. It shows at most the latest thirty returned UTC dates, sharing a scale within that chart; tiny nonzero values receive a minimum visible marker and exact values remain in the table. Unknown totals, missing amounts and observed zero stay distinct. These are returned dates, not a complete thirty-day period. Every returned date remains available in the explorer’s day selector and paged exact-value table.

The **Category and day explorer** uses observed date/category intersections from that same page. Choose a category to see its daily incoming and outgoing amounts, choose a UTC day to see its categories, or combine both selections. The selected daily chart shows at most the latest thirty matching returned dates, and the exact-value table has 100-row pages. All returned dates and categories remain selectable. Filters affect this explorer only; the returned-page totals and net chart keep their full-page scope. A missing intersection is absent evidence, not zero activity. Cells with no reported amounts remain unknown; mixed cells show their reported amounts and missing count. Filters make no additional requests, save no selections and reset when a new page or refreshed result loads.

In the private chat, `wallet_activity_report` returns the same page's totals, activity categories, coverage and freshness, with daily detail limited to the latest thirty returned UTC dates and explicit total/omitted date counts. Date counts remain unknown when the page cannot be read; a successfully read empty page has zero dates. The compact report omits the dashboard’s date/category cells. Supply an owned `characterId` and `entity`; corporation reads require a division from 1 to 7 and derive current corporation membership, while character reads forbid a division. Optional `page` defaults to 1. It uses the saved wallet grant, performs one journal-page read and never enables or captures saved history.

The **Industry → Mining ledger** view adds a daily bar chart for one selected material type across the displayed batch. Quantities for different types are never added together. The chart keeps real UTC date spacing, distinguishes reported zero from missing days, and offers an exact-value table. It uses the existing response and optional public labels, with no extra mining request or history store.

Analytics and manufacturing readers keep freshness unknown when an explicit `max-age` directive cannot be evaluated, including missing or invalid response dates. They do not fall back to a later `Expires` value in that case. Explicit `no-cache` and `no-store` remain stale, and valid evidence uses conservative expiry bounds. This follows the precedence in [HTTP caching rules](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.2.1); it adds no caching or collection.

These dashboards fetch only on request, hold results in memory, and clear them when selections change or the workspace is left. They reuse granted read permissions; no new scopes, database tables, write operations or credential settings are introduced. Current journal/mining windows and optional queue fields follow the [official ESI schema](https://esi.evetech.net/meta/openapi.json?compatibility_date=2026-10-31); freshness follows [CCP's caching guidance](https://developers.eveonline.com/docs/services/esi/best-practices/).

The `character_overview` chat tool returns the same personal overview as the dashboard for one owned connected character. Ask for a character briefing to get wallet balance, training, market orders, industry, contracts and freelance participation in one response. It requests only the six fixed feeds permitted by the saved read grants, under the existing shared deadline. Missing permissions, denied reads and partial coverage remain explicit; the tool never reconnects, changes scopes, captures history or fetches corporation data. Raw records, names and descriptions are omitted.

The **Overview** workspace shows one selected character at a time. Click **Load overview** to fetch wallet balance, skill queue, personal market orders, industry jobs, contracts and freelance jobs. Each card shows its own coverage and ESI cache information. Refreshes are manual; switching characters, workspaces or pages clears displayed results and cancels the browser request. Results are held in memory, with no account-data history, browser storage, background polling or new database tables.

The **Corporation operations** overview separately summarizes wallet balances, contracts, industry jobs, active projects, moon extraction schedules and freelance jobs. These overviews bound each dataset to one response. Each view shows coverage and source freshness. Wallet balances and order history reuse existing wallet/market read permissions; the other views use their optional permissions above.

Corporation project and freelance views show reported-state counts for all displayed rows and progress/target bars for the first twelve rows in table order, with explicit omissions. The selected character's contribution has a separate target ratio because it and project progress come from independent snapshots. None of these ratios proves completion, earned rewards or payout.

Structures keep fuel expiry, state timer end and unanchor time separate; extraction schedules keep chunk arrival and natural fracture separate. These charts do not request additional data or infer fuel quantities, structure power or destruction state, completed unanchoring, actual fracture, ore availability or mining yield. Refreshes remain manual.

Auction rows offer **Load bids** alongside **Load items**. Bids show the provider's reported amount and date, without bidder identities. Paging stays bound to the selected contract. Creator identities, contributor lists, descriptions, private docking locations and identity filters are omitted. Missing, unsupported or malformed objective details are marked explicitly; omitted filters mean the summary is incomplete, so review the full objective in EVE before acting. No contribution roster or extra permission is requested.

The **Assets** view reads one corporation asset page and displays up to 100 rows per slice. **Load details** rechecks that the selected item is still in that page before querying its custom name and available coordinates. No mail sending, contact editing, fleet commands or other game-changing operations are implemented.

## Clones and implants

The **Clones & implants** dashboard loads the selected character’s jump clones and active implants under their existing read permissions. Each feed has its own permission, error and cache status. Active implants remain separate from implants stored in jump clones; independently cached responses are not an atomic snapshot.

The jump-clone table and implant-count chart show response-local clone rows, reported location IDs/kinds and installed implant type entries. Loading this view reveals those clone and home-location IDs. Custom clone names and raw jump-clone IDs are omitted, and no location/name resolver is called. Implant labels come from the pinned public catalog, with exact type IDs and an explicit fallback for unmapped types. Repeated implant type entries remain reported occurrences rather than silently disappearing.

Reported clone-jump and station-change dates are shown as timestamps. Missing dates and optional home-location fields stay unknown. The dashboard does not infer jump readiness, clone capacity, implant bonuses, value or whether a facility is accessible. One load accepts at most 100 jump clones and 64 implant entries per clone or active-implant response; oversized or malformed feeds fail explicitly. Loads are manual, cancellable and clear on refresh, character changes or leaving the view. No account history, new permissions or game writes are added. See the [dated ESI schema](https://esi.evetech.net/meta/openapi.json?compatibility_date=2026-10-31) and [CCP’s jump-clone guide](https://support.eveonline.com/hc/en-us/articles/203217202-Jump-Clones) for provider fields and the separate in-game requirements.

In chat, `character_clone_report` reads those same two feeds for one owned character. It retains each feed's permission, status and freshness separately, with full accepted counts and previews of at most twenty active implant entries, twenty stored clones and eight implant entries per shown clone. Repeated type occurrences remain repeated, and omitted counts stay explicit. Public implant labels are limited to 128 Unicode characters with truncation flags; exact type IDs remain available. Custom clone names, persistent clone IDs, home and stored-clone locations are omitted. Unavailable sections remain unknown, and jump/station-change timestamps do not imply readiness, capacity, bonuses or value. The report adds no reads beyond the existing two feeds, settings, permissions, saved history or game writes.

## Calendar summaries

The **Calendar** workspace manually loads one connected character's next batch of at most fifty event summaries using the existing calendar read permission. Missing dates, responses, titles, importance values and event IDs remain explicit; importance is a reported number without an inferred priority meaning.

A short or empty response does not prove that the full calendar is complete. Missing or unchanged continuation IDs disable that continuation; no automatic paging or cross-batch history is added. Selection changes, refresh and leaving the view clear results and cancel outstanding requests.

## Build and run

The runtime is Vinext/React on Cloudflare Workers, with Cloudflare D1 storage and Sites hosting integration. It is not a standalone Next.js server.

Use Node.js **22.13.0 or newer** and **pnpm 11.25.0**. Install the locked dependencies from the project directory, including the build dependencies:

```sh
pnpm install --frozen-lockfile
pnpm dev
```

The portable preview normally uses `http://localhost:5173`. Its loopback-only mock sign-in supports local UI preview; it does not establish an EVE connection or production authentication. The optional connected-app preview bridge requires HTTP and a fixed port. It supports IPv4/IPv6 loopback and wildcard listeners while keeping bridge requests on loopback. HTTPS and remote-only listener settings fail explicitly; hosted connections use their separate runtime binding.

Build the application and run the built Worker locally with:

```sh
pnpm build
pnpm start
```

A production build writes `dist/server/wrangler.json`. The start command uses local Wrangler on loopback; it is not a production authentication gateway. Building or starting locally does not publish the application, apply hosted migrations or authorize EVE access. Follow the separate deployment instructions below for a private hosted installation.

The `install:ci` command supports the managed Linux/Sites environment and requires its shell utilities. Use the portable installation command above for an ordinary checkout. Keep the pinned dependency versions, lockfile and build configuration together when updating the source. Never distribute your installed directory, environment files, authorization database, logs or generated runtime state.

## Set up a separate deployment

Publishing source does not change a **private hosted deployment's** audience. Keep the deployment restricted to its intended owner, and configure a new environment for each separate installation:

1. Associate the checkout with your own new Sites project through the supported Sites workflow. Ensure `.openai/hosting.json` uses the new project's identity, the `mcp` capability and D1 binding `DB`.
2. Provision a separate D1 database and apply the migrations in `drizzle/` through that workflow.
3. Set `EVE_SITE_ORIGIN` to the exact HTTPS origin of your deployment.
4. Generate a fresh cryptographically random 32-byte key, encode it in standard base64, and store it as the hosted secret `EVE_TOKEN_KEY`. Keep it out of source, build artifacts and logs. Do not reuse another deployment's key or authorization database.
5. Publish using the supported Sites source and build workflow, retaining the private audience and authentication gateway.
6. Register your own EVE developer application. Use the deployment origin as its website and `${EVE_SITE_ORIGIN}/eve/callback` as its callback URL. Add the read scopes shown by the setup page.
7. Enter that application's public Client ID on the private setup page and complete EVE sign-in for each character. Select corporation access only when needed. This implementation does not collect an EVE password or store an EVE client secret.
8. Verify connection status and actual authorized reads through your deployment's plugin.

For an existing installation, preserve its encryption key unless performing a deliberate rotation: replacing it makes saved encrypted authorizations unreadable and requires affected characters to reconnect.

## Authentication and data handling

Production routes trust the `oai-authenticated-user-id` header supplied by the Sites gateway. **Do not expose the worker as a raw public server or put it behind an untrusted proxy.** The authentication gateway must prevent callers from forging trusted identity headers and enforce the deployment's audience. Local mock sign-in does not provide these guarantees.

Tokens and PKCE verifiers are encrypted on the server. Connection metadata, including character names and IDs, is stored separately. Authorized read results are returned to the calling client; treat account data, chat exports and database backups as private.

Disconnect removes the connector's stored authorization and cancels that user's pending sign-ins, so an earlier callback cannot restore the removed connection. Start a fresh sign-in when reconnecting. Revoking the application grant at EVE is a separate action. See [SECURITY.md](SECURITY.md) for deployment and disclosure guidance.

## Data limits

EVE caches API responses and limits historical availability. Follow pagination and wallet transaction cursors before computing totals. Transaction cursors include their boundary record: deduplicate transaction IDs when combining manually requested batches, and request the next batch only when `nextFromId` is non-null. An unchanged or forward-only batch now returns a null continuation. This means no further backward cursor was established, not that complete history was returned. See [CCP’s inclusive cursor documentation](https://developers.eveonline.com/docs/services/esi/pagination/from-id/). Corporation wallet transaction and journal reads cover one selected division at a time; balance reads report the returned divisions with explicit coverage. Public regional market books can omit private structure orders. The application does not provide a long-term transaction archive or recurring polling.
